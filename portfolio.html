운영 과정에서 반복된 결제 정합성 문제의 코드와 영향 범위를 추적해 구조적 원인을 분석했습니다. 대표·기획과 결제 정책을 확정한 뒤 클라이언트부터 서버·DB까지 전체 결제 흐름을 단독으로 설계하고 구현했습니다.

문제 인식

클라이언트가 결제 확정을 담당하던 구조에서는 결제 승인과 주문 기록 사이에 상태 불일치가 발생할 수 있었습니다. 기존 코드를 추적한 결과, 결제 확정 이후 서버 검증과 주문 저장을 요청하는 순서 때문에 중간 실패 시 두 시스템의 상태가 어긋날 수 있었습니다.

분석

사후 보정만으로는 구조적인 재발을 막기 어렵다고 판단했습니다. 결제 금액과 주문 상태는 서버에서만 확정하고, PG 지연이나 타임아웃이 발생해도 요청을 실패로 단정하지 않고 최종 상태를 추적할 수 있어야 했습니다.

실행

  • 대표·기획과 유료·무료 주문 및 환불 정책을 확정하고, 클라이언트부터 서버·DB까지 전체 결제 흐름을 단독으로 구현했습니다.
  • 주문 생성 단계에서 서버가 계산한 최종 금액과 클라이언트 요청 금액을 먼저 검증하고, 이후 Redis 세션의 가격 정보로 한 번 더 검증했습니다.
  • 서버에 WAITING_PAYMENT 상태를 도입해 결제 시도 단위의 주문번호를 먼저 고정하고, 재시도·재진입에도 동일 주문으로 처리되도록 멱등성을 보장했습니다.
  • Bootpay confirm 타임아웃 시 PROCESSING 응답을 반환하고, 주문 상태 조회 API로 폴링할 수 있는 흐름을 추가했습니다.
  • CARD 결제와 FREE 주문을 분기 처리해 무료 주문은 Bootpay 검증 없이 완료하고, 무료 주문에서도 정합성이 깨지지 않도록 로직을 수정했습니다.

결과

  • 2026년 3월 서버 중심 결제 구조 전환 이후 내부 결제 정합성 이슈 재발 0건을 유지하고 있습니다.
  • 주문 생성, 결제 확정, 환불 정책의 책임을 서버로 일원화해 운영자가 같은 주문번호 기준으로 결제 상태를 추적할 수 있게 했습니다.

외부 채팅 서비스 교체에 그치지 않고 서버, 인프라, 두 종류의 클라이언트를 하나의 전환 계획으로 설계했습니다. 전체 시스템 구조를 주도하고 REST API 서버, React Native·Flutter 클라이언트와 CDK 기반 인프라를 직접 구현해 Closer의 약 500개 활성 채팅방을 자체 서버로 전환했습니다.

문제 인식

외부 채팅 서비스는 빠른 도입에는 유리했지만, 사용자 규모가 커질수록 비용 부담이 커졌고 푸시, 금칙어, 제재, 백오피스 모니터링 같은 내부 운영 정책을 세밀하게 반영하기 어려웠습니다.

분석

기존 채팅을 즉시 대체해야 하는 상황은 아니었기 때문에 출시 일정보다 메시지 정합성과 운영 안정성을 우선했습니다. REST 요청과 실시간 연결의 책임을 분리하고, 메시지 순서와 누락 복구는 서버가 발급한 messageId를 기준으로 맞췄습니다.

실행

  • 전체 시스템 구조를 설계하고 REST API 서버, React Native·Flutter 클라이언트 연동, CDK 기반 인프라를 구현했습니다.
  • REST 서버와 WebSocket 서버를 분리해 요청 처리와 실시간 연결 책임을 나눴습니다.
  • PostgreSQL에 메시지를 저장하고 Redis Pub/Sub으로 WebSocket 다중 노드를 동기화했습니다.
  • messageId 기준 정렬, 재연결 gap recovery, 읽음 커서 기반 unread count로 메시지 정합성을 맞췄습니다.
  • Closer의 약 500개 활성 채팅방을 자체 서버로 전환해 외부 서비스 비용을 월 약 300달러 절감했습니다.

결과

  • Sendbird 의존도를 낮추고 채팅 운영 정책을 내부에서 통제할 수 있는 기반을 만들었습니다.
  • 1차 전환으로 월 약 300달러를 절감하고, 2차 전환 시 월 약 1,700달러를 추가로 절감할 수 있는 경로를 만들었습니다.
  • 메시지 저장, 읽음 처리, 푸시, 백오피스 모니터링을 서비스 정책에 맞게 확장할 수 있게 했습니다.

메인 화면과 모임 탐색부터 상세, 결제, 마이페이지 결제 내역까지 웹의 핵심 사용자 흐름을 설계하고 구현했습니다. 별도 광고 집행 없이 출시 후 약 3개월 만에 웹 월간 활성 사용자가 8만에서 12만으로 증가했습니다.

문제 인식

기존 웹은 서비스 소개와 앱 설치 유도가 중심이어서, 검색이나 공유 링크로 유입된 사용자가 모임을 탐색하고 결제하려면 앱으로 이동해야 했습니다. 이 전환 과정의 높은 진입 장벽 때문에 웹 유입이 실제 서비스 이용으로 이어지기 어려웠습니다.

분석

랜딩 페이지의 완성도를 높이는 것보다 웹 자체를 하나의 서비스 접점으로 만드는 것이 필요하다고 판단했습니다. 기존 앱 API를 활용하되, React Query 캐시를 중심으로 서버 상태를 관리하고 UI 상태는 로컬 훅으로 분리해 웹의 프론트엔드 구조를 설계했습니다.

실행

  • 문토 메인, 모임 모음과 소셜링 상세, 결제, 마이페이지 결제 내역 등 핵심 프론트엔드 흐름을 대부분 직접 설계하고 구현했습니다.
  • 로그인 상태와 서비스 데이터를 안정적으로 다룰 수 있는 상태 관리 구조를 정리해 주요 화면 경험을 일관되게 맞췄습니다.
  • 웹에서 구현한 핵심 화면을 앱에서도 재사용할 수 있도록 연결 구조를 정리해 플랫폼별 기능 중복을 줄였습니다.

결과

  • 별도 광고 집행 없이 출시 후 약 3개월 만에 웹 월간 활성 사용자가 8만에서 12만으로 증가했고, 전체 월간 활성 사용자는 25만+ 규모로 확장됐습니다.
  • 검색 유입 확대와 앱 설치 없이 결제까지 이어지는 낮아진 진입 장벽이 성장에 함께 영향을 준 것으로 판단했습니다.
  • 모바일 웹, 데스크톱 웹, 앱 웹뷰 3개 접점의 사용자 흐름을 일관되게 맞춰 기능 확장 시 혼선을 줄였습니다.
  • 웹에서 구현한 VOD 경험을 앱 상세/플레이어 화면에서도 재사용할 수 있게 만들어 동일 기능을 플랫폼별로 다시 구현하는 비용을 줄였습니다.
  • 웹뷰 기반 재사용 구조를 정리해 앱 안에서도 웹 기능이 끊기지 않도록 연결했습니다.

AI 에이전트를 활용하면 구현 속도는 빨라질 수 있지만, 개발 프로세스가 먼저 정립되어 있지 않으면 설계 없이 코드부터 작성하거나 백엔드, 프론트엔드, 모바일 산출물이 서로 다른 기준으로 만들어질 위험이 있었습니다. 특정 에이전트에서만 가능한 프롬프트가 아니라 어떤 AI 도구에서도 반복 가능한 개발 흐름이 필요했습니다.

분석

단순한 프롬프트 모음으로는 요구사항, 설계 산출물, 구현 코드, 테스트 케이스의 정합성을 유지하기 어렵다고 판단했습니다. 그래서 먼저 기획/SRS → WBS → 설계(DBML, Swagger, TCL) → 도메인별 구현 → 검증으로 이어지는 표준 개발 프로세스를 주도적으로 정립하고, 에이전트는 이 프로세스를 실행하는 역할로 두는 구조를 설계했습니다.

실행

  • 각 단계의 입력값, 산출물, 완료 조건을 정의해 AI 에이전트가 임의로 순서를 건너뛰지 않고 같은 흐름을 따르도록 했습니다.
  • 설계 단계에서는 DBML, Swagger, TCL writer를 분리하고, 산출물 간 정합성을 검증하는 reviewer agent 흐름을 구성했습니다.
  • 백엔드, 프론트엔드, 모바일 구현 단계는 domain expert sub-agent로 분리해 각 도메인의 개발 순서와 컨벤션을 독립적으로 준수하도록 설계했습니다.
  • Claude, Cursor, Codex 등 도구별 차이는 어댑터로 흡수하고, 실제 프로세스와 규칙은 공통 원본을 참조하게 구성했습니다.
  • 최종 검증 단계에서는 TCL 기반 Unit Test, E2E, 수동 체크리스트를 통해 요구사항과 구현 결과를 다시 연결했습니다.

결과

  • 설계를 주도하고 고문과 함께 보완한 표준 개발 프로세스를 AI 에이전트가 재현 가능한 형태로 시스템화했습니다.
  • 역할 기반 sub-agent orchestration을 통해 어떤 AI 에이전트를 사용하더라도 동일한 단계, 산출물, 검증 기준에 따라 개발을 진행할 수 있는 구조를 만들었습니다.
  • 설계 산출물, 구현 코드, 테스트 케이스가 하나의 흐름으로 연결되어 산출물 누락과 명세 불일치를 줄였습니다.
  • 하네스를 적용한 1~2개 사내 프로젝트에서 WBS 예상 일정 대비 약 60% 빠르게 산출물을 완성했습니다.
  • 검증된 흐름을 팀 표준으로 채택해 현재 모든 팀원이 같은 개발 기준으로 사용하고 있습니다.

표준 개발 프로세스

1 기획/SRS를 기준으로 요구사항과 범위 정리
2 WBS 작성 후 설계 산출물(DBML, Swagger, TCL) 생성
3 백엔드 / 프론트엔드 / 모바일 영역별 구현 순서 적용
4 TCL 기반 Unit Test, E2E, 수동 체크리스트로 검증
5 요구사항 → 설계 → 구현 → 테스트가 이어지는 개발 흐름 완성

에이전트 실행 구조

1 메인 에이전트가 SRS, Swagger, TCL, 작업 범위를 확인
2 dev-chain 스킬이 단계별 입력값, 산출물, 완료 조건을 제공
3 백엔드 / 프론트엔드 / 모바일 전문 하위 에이전트가 영역별 개발 순서를 준수
4 Reviewer agent가 설계 산출물 정합성과 누락 항목을 검증
5 어떤 AI 도구에서도 같은 개발 프로세스를 반복 실행

서로 다른 데이터 모델을 일관된 인터랙티브 차트 경험으로 통합

단독 설계·구현 · 5개 건강 지표를 공통 인터페이스로 추상화

신규 건강 데이터 기능을 지표별 화면의 집합으로 만들지 않고, 데이터 형태와 그래프 구현을 분리한 하나의 차트 시스템으로 설계했습니다. 단일값과 복합값을 공통 인터페이스로 추상화해 새로운 지표가 추가돼도 렌더링과 인터랙션 구조를 재사용할 수 있게 했습니다.

문제 인식

혈압, 체중, 신장, 혈당, BMI를 새로 제공하면서 지표별 화면을 각각 만들면 계산 로직과 인터랙션이 쉽게 분기될 수 있었습니다. 초기 구현 속도뿐 아니라 이후 건강 데이터가 추가될 때의 변경 비용까지 고려해야 했습니다.

분석

서버 DTO를 화면에 직접 연결하지 않고 앱 모델로 변환한 뒤, 단일값과 복합값이라는 데이터 형태를 공통 인터페이스로 추상화했습니다. 그래프 인터페이스와 실제 렌더링 구현체도 분리해 데이터 종류와 표현 방식이 서로 독립적으로 확장되도록 설계했습니다.

실행

  • 전체 차트 구조를 단독으로 설계하고 서버 DTO, 앱 모델, 그래프 인터페이스와 구현체의 책임을 분리했습니다.
  • 체중·신장 같은 단일값과 여러 값을 함께 표현하는 복합 데이터를 공통 차트 모델로 변환했습니다.
  • CustomPainter와 GestureDetector 기반으로 차트 렌더링과 줌/스와이프 인터랙션을 직접 구현했습니다.

결과

  • 혈압, 체중, 신장, 혈당, BMI 5개 지표를 하나의 차트 시스템으로 일관되게 표현했습니다.
  • lerp 기반 애니메이션과 제스처 처리로 요구사항에 맞는 차트 UX를 구현했습니다.
  • 차트 로직의 재사용성과 확장성이 높아져 이후 건강 데이터 타입을 추가하기 쉬워졌습니다.

구현 흐름

1 혈압, 체중, 신장, 혈당, BMI 등 각기 다른 DTO 입력
2 DTO와 앱 모델 레이어 분리 + Mapper 규칙 정의
3 단일값 / 복합값 인터페이스 기반 공통 차트 모델로 변환
4 CustomPainter 기반 렌더링
5 GestureDetector 기반 줌 / 스와이프 / 선택 인터랙션 적용
6 동일 구조 재사용으로 일관된 인터랙티브 차트 UX 구현
